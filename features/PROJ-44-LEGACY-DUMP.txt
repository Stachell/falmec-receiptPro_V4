# PROJ-44 ADD-ON Round 12: Race-Condition Kill — Self-Advance-Pattern

**Status:** PLAN (noch keine Code-Aenderungen)
**Datum:** 2026-04-01
**Scope:** `src/store/runStore.ts`, `src/services/stepGuard.ts`
**Ausloeser:** Round 9 Diagnostic — Timer-basierte Race-Conditions in Auto-Advance-Logik

---

## 1. Problemanalyse

### 1.1 Die drei Gefahren

**Gefahr A — Timer-Race (Workflow-Stall):**
`executeMatcherCrossMatch()` hat eine sync Signatur, feuert aber intern `runAsyncStep2()` (async IDB-Read + Matcher-Logik). Der 100ms-Advance-Timer (`t2adv`, Zeile 2226) feuert 100ms nach dem sync Return von `executeMatcherCrossMatch()`. Wenn die async IDB-Operation > 100ms dauert, sieht der Timer Step 2 noch als `running` → Bedingung `status === 'ok'` ist false → **advanceToNextStep wird nie aufgerufen → Workflow haengt.**

**Gefahr B — Blinder Advance (Step-Skip):**
`advanceToNextStep(runId)` (Zeile 2174) sucht den aktuell `running` Step und setzt ihn auf `ok`. Wenn ein verspaeteter Timer-Callback feuert waehrend der naechste Step schon laeuft, wird der FALSCHE Step auf `ok` gesetzt und uebersprungen.

**Gefahr C — Step-3-Guard-Luecke:**
`runStepGuard()` (Zeile 732) ruft `validateStepPrerequisites()` auf, die fuer Step 3 den **synchronen** `validateStep3()` (Zeile 201) dispatcht. Die SSOT-sichere **asynchrone** Variante `validateStep3Async()` (Zeile 118) existiert in `stepGuard.ts`, wird aber nie von `runStepGuard` aufgerufen. Der sync-Fallback kann keinen IDB-Check machen und liefert fuer SSOT-Runs unzuverlaessige Ergebnisse.

### 2.3 Idempotenz-Garantie (Erklaerung)

Der **Idempotenz-Guard** (`alreadyRunning`) verhindert Double-Advance:

| Szenario | Ergebnis |
|---|---|
| 1. Aufruf: Step 2 `ok`, kein Step `running` | Startet Step 3 → Step 3 wird `running` |
| 2. Aufruf (verspaetet): Step 2 `ok`, Step 3 ist `running` | `alreadyRunning = true` → **Bail out** (Idempotent) |
| Execute-Funktion setzt Step auf `failed` | `completedStep.status !== 'ok'` → **Bail out** (kein Advance) |

## 5. Architektur-Gegencheck: Seiteneinstiege

### 5.1 `retryStep` (Zeile 2553)

**Aktuell:** ~50 Zeilen mit 3 setTimeout-Bloecken, KEIN Advance nach Retry (bewusst — User soll Ergebnis pruefen).

**NEU mit Self-Advance:** `retryStep` feuert Guard + Execute-Funktion. Die Execute-Funktion ruft am Ende `advanceToNextStep(runId, stepNo)` auf. **Aenderung:** Workflow laeuft nach erfolgreichem Retry automatisch weiter (Steps 3→4→5 kaskadieren). Dies ist das gewuenschte Verhalten — ein erfolgreicher Retry soll den Workflow fortsetzen, nicht haengen bleiben.

### 5.2 `resumeRun` (Zeile 3011)

**Aktuell:** ~250 Zeilen — komplette Kopie der advanceToNextStep-Timer-Logik fuer Step 2/3/4.

**NEU mit Self-Advance:** Dramatisch vereinfacht. `resumeRun` findet den `running` Step und feuert dessen Execute-Funktion. Self-Advance kaskadiert automatisch.

**Vereinfachter resumeRun:**
```typescript
resumeRun: (runId) => {
  set({ isPaused: false });
  get().updateRunStatus(runId, 'running');
  logService.info('Run fortgesetzt', { runId, step: 'System' });

  const run = get().runs.find(r => r.id === runId);
  if (!run) return;
  const runningStep = run.steps.find(s => s.status === 'running');
  if (!runningStep) return;

  // Step 5 hat keine Execute-Funktion → direkt abschliessen
  if (runningStep.stepNo === 5) {
    get().generateStep5Issues(runId);
    get().advanceToNextStep(runId);
    return;
  }

  // Steps 2-4: Guard + Execute → Self-Advance kaskadiert
  void (async () => {
    const guard = await runStepGuard(runningStep.stepNo, runId, get, set);
    if (guard.blockReason) {
      logService.error(`[StepGuard] Resume Step ${runningStep.stepNo} blockiert: ${guard.blockReason}`, { runId, step: runningStep.name });
      get().updateStepStatus(runId, runningStep.stepNo, 'failed');
      return;
    }
    if (guard.skipReason) {
      logService.info(`[StepGuard] Resume Step ${runningStep.stepNo} uebersprungen: ${guard.skipReason}`, { runId, step: runningStep.name });
      get().updateStepStatus(runId, runningStep.stepNo, 'ok');
      get().advanceToNextStep(runId, runningStep.stepNo);
      return;
    }

    switch (runningStep.stepNo) {
      case 2:
        logService.info('Resume: Matcher Cross-Match (Step 2)', { runId, step: 'Artikel extrahieren' });
        get().executeMatcherCrossMatch();
        break;
      case 3:
        logService.info('Resume: Matcher Serial-Extraktion (Step 3)', { runId, step: 'Seriennummer anfuegen' });
        await get().executeMatcherSerialExtract();
        break;
      case 4:
        // Step 4 Sonderlogik: identisch zu advanceToNextStep Step-4-Block
        // → SSOT/Legacy/OpenWE Orchestrierung (siehe 5.4)
        break;
    }
    // Self-Advance geschieht am Ende der Execute-Funktionen
  })();
},
```

## 9. Zu verifizierende Circuit-Verdrahtungen (Temporärer Parkplatz)

> Aus CIRCUIT.md Sektion B entfernt am 2026-04-02. Zur späteren Verifikation geparkt.

**B1. executeMatcherCrossMatch → Status-Setzung ohne updateStepStatus am Erfolgsende**
`CONFI: MID` — executeMatcherCrossMatch setzt bei Fehler updateStepStatus(2, 'failed'), aber bei Erfolg setzt die AUFRUFENDE Stelle in advanceToNextStep den Status. Die Funktion selbst hat keinen expliziten 'ok'-Aufruf am Ende.
`QUELLE:` CIRCUIT-Scan 2026-04-02
```
executeMatcherCrossMatch()
  ├─ Fehler-Pfade: updateStepStatus(runId, 2, 'failed') → intern ✓
  └─ Erfolg-Pfad: KEIN updateStepStatus(runId, 2, 'ok') → 
     Caller (advanceToNextStep/retryStep) muss 'ok' setzen + advance triggern
     → Asymmetrisch zu executeOrderMapping (setzt 'ok' selbst bei Empty-Lines)
```

**B4. Step-3-Guard: Sync-Wrapper vs Async-Variante**
`CONFI: MID` — validateStepPrerequisites ruft validateStep3 (sync), aber runStepGuard für Step 3 in advanceToNextStep nutzt den sync-Pfad. Die async-Variante validateStep3Async existiert in stepGuard.ts, wird aber von advanceToNextStep NICHT direkt aufgerufen — der IDB-Check passiert stattdessen implizit über applyStepRepairs.
`QUELLE:` CIRCUIT-Scan 2026-04-02
```
Step 3 Guard-Pfad:
  runStepGuard(3, ...)
    → validateStepPrerequisites(3, ...) → validateStep3 (SYNC, kein IDB)
    → [!canProceed] → applyStepRepairs → serialData-Reparatur aus IDB
  
  validateStep3Async existiert ABER wird nirgends aufgerufen
  → Dead Code oder geplanter Umbau?
```

**B6. executeOrderMapping → Interne Status-Setzung (gemischt)**
`CONFI: MID` — executeOrderMapping setzt Status direkt via set() UND via updateStepStatus, abhängig vom Pfad. Bei Empty-Pool wird status in einem atomaren set() gesetzt, bei Normal-Erfolg in einem separaten set(). Der Status wird NIE via updateStepStatus('ok') am Ende gesetzt — nur via step-Status im runs-Update.
`QUELLE:` CIRCUIT-Scan 2026-04-02
```

  ├─ Empty-Lines:    updateStepStatus(runId, 4, 'ok') → return
  ├─ SSOT no-pool:   updateStepStatus(runId, 4, 'failed') → return
  ├─ Empty-Pool:     direktes set() mit status='failed' in Run-Objekt
  ├─ Engine-Erfolg:  direktes set() mit status='ok'|'soft-fail' in Run-Objekt
  └─ catch:          updateStepStatus(runId, 4, 'failed')

  → Zwei verschiedene Mechanismen für Status-Updates (updateStepStatus vs set)
```
